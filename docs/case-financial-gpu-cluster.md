# 案例：一台 8×H20 节点上的 LLM 推理服务治理

> 一家金融机构（信息已脱敏）在离线私有云上用一台 8 卡 H20（单卡 96GB）节点支撑全公司的 AI 推理负载。本案例记录其集群拓扑、部署形态与一次系统化配置审计的发现——**它同时是"原则 2：减少人工中转、保留人工问责"和"先度量再调参"的实践样本**。

## 1. 背景与约束

- **离线环境**：节点无法访问公网，模型与镜像全部内部分发；
- **算力上限**：1 机 8 卡就是全部预算，加卡不可行；
- **调度粒度**：平台按 pod 分配 GPU，每个 pod 可得 1/2/4/8 卡，总数 8；
- **真实压力**：全员把 Agent 客户端（DSH 类 harness）默认指向最强的 DeepSeek 推理服务，日常并发 40 超过引擎槽位 32，排队劣化持续发生，而 nobody 自愿迁移到备用模型。

## 2. 集群拓扑：4+2+1+1 为什么是"被锁死的唯一解"

四个服务、粒度 {1,2,4,8}、总数 8 的约束下推演：

- 旗舰服务（DeepSeek 级大 MoE，权重 TP4 下约 50GiB/卡）**物理上放不进 2 卡** → 锁死 4 卡；
- 4 个服务各需 ≥1 卡 → 唯一有意义的变体是"备用服务降 1 卡换其他服务升 2 卡"，但这与"让备用服务承接分流"的目标正面冲突。

**教训**：GPU 卡数再分配这个杠杆在"服务数 × 粒度"约束下常常是死的——优化的主战场在卡数之外（参数、流量、缓存）。

| Pod（匿名） | 卡数 | 服务形态 | 关键参数 |
|---|---|---|---|
| `llm-chat` | 4 | 旗舰大模型（TP4+EP，FP8 出厂，196K 上下文，投机解码×5） | max-num-seqs 32；util 0.9 |
| `llm-chat-lite` | 2 | 中型主力（27B 级，TP2，BF16，128K，MTP×2） | max-num-seqs 96；util 0.92 |
| `llm-file-parser` | 1 | 文档解析（视觉管线 + 格式转换双容器） | tier 自动探测 |
| `llm-retrieval` | 1 | 检索双件（embedding :8002 + reranker :8003 单容器双实例） | 各 util 0.45 共卡 |

## 3. 部署形态的两条路线（同一集群并存）

- **镜像与权重分离**（chat/lite/retrieval）：权重放 NAS，镜像只含引擎。换模型 = 改路径 + 滚动重启，不动镜像——权重级升级变成低成本动作；
- **镜像与权重打包**（file-parser）：解析管线与 VLM 权重烤进镜像。每次版本升级 = 重建并分发数十 GB 镜像。两种路线的取舍（升级频率、镜像分发成本、缓存命中）本身就是 AI-Native 化的基建决策题。

检索 pod 的 `MODELS` 环境变量是单容器多实例的典型形态（节选，已脱敏）：

```yaml
env:
- name: MODELS
  value: |
    [
      { "name": "embedding",
        "command": ["python3","-m","vllm.entrypoints.openai.api_server",
          "--model","/data/models/Qwen3-Embedding-4B",
          "--port","8002","--gpu-memory-utilization","0.40",
          "--task","embedding"] },
      { "name": "reranker",
        "command": ["python3","-m","vllm.entrypoints.openai.api_server",
          "--model","/data/models/Qwen3-Reranker-4B",
          "--port","8003","--gpu-memory-utilization","0.28","--enforce-eager",
          "--task","score",
          "--hf_overrides","{\"architectures\":[\"Qwen3ForSequenceClassification\"],\"classifier_from_token\":[\"no\",\"yes\"],\"is_original_qwen3_reranker\":true}"] }
    ]
```

这段配置里藏着一个典型事故：reranker 曾用 `--task embedding` 起（分数语义退化为余弦相似度而非模型训练的 yes/no 判别），以及一个静默回归（embedding 实例丢了 `--task embedding` 会导致向量端点整体 404）。**"服务活着"与"语义正确"是两件事**——这正是需要契约测试与语义验收的原因。

## 4. 配置审计发现的六类典型问题

对上述集群做的一次系统化审计（逐 pod 参数 × 运行取证），发现的问题高度模式化：

| # | 问题 | 根因 | 修正方向 |
|---|---|---|---|
| 1 | 仅 liveness 探针，无 readiness/startup | 用 initialDelay 常数猜冷启动时长 → 滚动更新流量黑洞 + 慢载死循环风险 | 探针三件套（startup 容忍分钟级冷启 / readiness 挡滚动流量 / liveness 放宽防误杀） |
| 2 | util 0.90~0.92 贴顶且无压测记录 | 决策无证据链；大 batch 激活峰值可击穿余量（实测发生过运行期 OOM 10 小时无人察觉） | 压测阶梯定档 + 显式 max-num-batched-tokens 封顶激活 |
| 3 | 投机解码 ×2 与 96 并发槽位同配 | 两个参数各自描述相反的服务形态（投机低批量最优 / 大槽位为高并发而生） | 接受率×并发曲线分档；adaptive verification |
| 4 | 96×128K 的容量口径失真 | 名义积远超 KV 池；真实并发 = KV 池 ÷ 平均上下文 | 按真实负载口径重算并公布；加排队上限 |
| 5 | 检索双实例任务语义错配 | `--task` 旗标的语义分叉（embedding=余弦 / score=判别概率），接口能通但分数是错的 | 语义验收进上线清单（已知对分数形态比对） |
| 6 | 引擎版本与模型架构代际错配 | 新架构（GDN 混合注意力）跑在早期引擎版本上，后续修复未吃到 | 版本升级回归清单化 |

**共同根因只有一条：配置交付时没有证据链（压测曲线 / 语义验收 / 取证记录）。**修每一项时把证据一并落账，是让组织从"按模板拍脑袋"走向"可审计运维"的最短路径。

## 5. 与三条原则的对齐

- **原则 2（减少人工中转、保留人工问责）**：探针三件套的本质是把"服务是否可用"的判定从人工盯梢交给系统；而 liveness/readiness/startup 的分工保留了"何时该重启"的明确责任边界。
- **先度量再调参**（制造业剧本中 1911 泰勒制的回声）：问题 2/3/4 的修正全部指向同一个动作——先建立"接受率、激活峰值、真实并发"的度量，再动参数。没有度量的调参是占卜。
- **接口标准化**：问题 5 说明"HTTP 200 + 返回分数"不构成验收——语义契约（分数分布形态、已知输入的期望输出）才是。
